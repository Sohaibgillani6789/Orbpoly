## 1. Detailed Implementation: Networking & Performance

### Client-Side Prediction & Server Reconciliation
To prevent the game from feeling sluggish, the client must never wait for the server to confirm movement.
1. **Input Handling:** When a player presses a movement key or attacks, the client immediately updates the local Three.js character mesh and plays the animation.
2. **Sequencing:** The client assigns a unique `sequenceNumber` to this input and sends it to the server (`socket.emit('input', { seq: 12, action: 'move_left' })`). It also stores this in a local `pendingInputs` array.
3. **Reconciliation:** When the server sends an authoritative state update back to the client, it includes the `lastProcessedSeq`. The client removes all inputs up to that sequence from `pendingInputs`. If the server's position differs from the client's current position, the client snaps the character to the server's position, then instantly re-applies any remaining `pendingInputs` to hide the correction from the player.

### Entity Interpolation (Smooth Enemy Movement)
Enemies will look like they are teleporting if you just set their Three.js mesh position every time a Socket.io packet arrives.
1. **Buffer States:** When the client receives data about the other 5 players, it pushes that data into a `stateBuffer` array, tagged with the server timestamp.
2. **Render in the Past:** The client’s render loop looks at a time slightly in the past (e.g., `renderTime = serverTime - 100ms`).
3. **Lerp:** The client finds the two server states in the buffer that bracket `renderTime` (one just before, one just after). It uses `THREE.Vector3.lerp()` and `THREE.Quaternion.slerp()` to smoothly animate the enemy's Three.js meshes between those two points.

### Server Rewind (Lag Compensation)
This solves the "Ghost Hit" problem where a player punches an enemy on their screen, but the server rejects it due to ping.
1. **The History Buffer:** The Node.js server maintains an array of position/animation states for all players spanning the last 500ms.
2. **Timestamped Attacks:** When Player A attacks, they send the attack packet along with the exact time the attack happened on their screen.
3. **The Rewind:** The server receives the packet 50ms later. It looks at the packet's timestamp, goes into its History Buffer, and moves Player B's hitboxes back to where they were 50ms ago.
4. **Collision Check:** The server performs the `Sphere` overlap math in the past. If it's a hit, the server applies damage and snaps Player B back to the present.

### Hitboxes vs Hurtboxes in Three.js
Do not use `THREE.Raycaster` against complex character meshes (GLTF/FBX) for 6 players on a server.
1. **Hurtboxes:** Attach `THREE.Sphere` objects to the character's skeleton (Head, Torso, Legs). These are blue and always active.
2. **Hitboxes:** Attach a `THREE.Sphere` to the character's hands or feet. These are red and are only scaled up/activated during specific frames of an attack animation.
3. **Server Math:** The server does not need to run Three.js. It just stores the center `x,y,z` and `radius` of these spheres. A hit occurs if `DistanceBetweenCenters < (HitboxRadius + HurtboxRadius)`.
