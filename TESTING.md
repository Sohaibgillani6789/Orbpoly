# Orbpoly — TESTING.md\n\n> Senior Three.js/WebGL debugging, QA, and code-quality specification.\n> Goal: find and fix errors, improve syntax and maintainability, and prove the game is stable without changing design, graphics, gameplay, controls, character roster, floating-island composition, grass density, sky, or day/night behavior.\n\n## 1. Non-negotiable rules\n- This is debugging, correctness, testing, and code-quality work.\n- Never redesign the game.\n- Never remove characters, grass, sky effects, combat, physics behavior, or visual effects to hide errors.\n- Never fix an error by suppressing it, deleting the failing feature, or using an empty catch.\n- Make the smallest safe change that fixes the root cause.\n- Preserve existing behavior after every fix.\n\n## 2. Repository audit already performed\nThe repository was searched before writing this specification.\n\nKnown areas requiring attention:\n- src/script.js contains loading, audio, grass, sky, mood/day-night, GUI, tree, rock, character loading, and scene startup responsibilities.\n- console.log/console.error calls exist in src/script.js, GameManager.js, NetworkManager.js, AnimationStateMachine.js, RemotePlayerController.js, server/server.js, and server/GameRoom.js.\n- lil-gui is instantiated from the main client entry point and should be verified as development-only.\n- asynchronous character preview loading exists and must be checked for race conditions.\n- InputManager and PerfMonitor register browser event listeners and require lifecycle auditing.\n- package.json currently provides build/dev/preview/deploy scripts but no explicit lint or test script.\n\n## 3. Baseline before edits\nRun the real project before changing code:\n\n~~~bash\nnpm install\nnpm run build\nnpm run dev\n~~~\n\nAlso test the production build with npm run build followed by npm run preview.\n\nRecord, without inventing results:\n- build success/failure;\n- browser console errors;\n- browser console warnings;\n- uncaught exceptions;\n- unhandled promise rejections;\n- failed network requests;\n- missing assets;\n- shader compilation errors;\n- WebGL errors;\n- multiplayer errors;\n- visible gameplay regressions.\n\n## 4. Zero-error production target\nNormal production gameplay should reach:\n- 0 uncaught exceptions;\n- 0 unhandled promise rejections;\n- 0 shader compilation errors;\n- 0 missing required assets;\n- 0 duplicate initialization errors;\n- 0 unexplained network failures;\n- 0 debug console spam.\n\nWarnings are not automatically harmless. Investigate every warning and classify it as intentional, actionable, browser-specific, deprecated, or defective.\n\n## 5. Repository-wide error search\nSearch all source and server files for:\n\n~~~text\nconsole.log\nconsole.warn\nconsole.error\nconsole.debug\ndebugger\nthrow new\nPromise\n.catch(\n.then(\nasync\nawait\nsetTimeout\nsetInterval\nrequestAnimationFrame\naddEventListener\nremoveEventListener\nsocket.on\nsocket.emit\nTextureLoader\nGLTFLoader\nOBJLoader\nAudioLoader\nnew THREE.\nnew CANNON.\nTODO\nFIXME\nHACK\nTEMP\nXXX\n~~~\n\nReview every empty catch, ignored promise, timer, event listener, and error callback.\n\n## 6. Syntax and static code quality\nAudit every JavaScript module for:\n- undeclared variables;\n- duplicate declarations;\n- invalid imports/exports;\n- unused imports;\n- unused variables;\n- shadowed variables;\n- unreachable code;\n- inconsistent return values;\n- accidental globals;\n- missing error paths;\n- stale comments;\n- misleading names;\n- unnecessary nested callbacks;\n- incorrect async/await usage;\n- circular dependencies.\n\nDo not perform a repository-wide formatting rewrite just for style. Keep diffs focused.\n\n## 7. Linting\nIf no lint system exists, introduce a lightweight ESLint configuration suitable for the existing JavaScript project.\n\nRequired objective:\n\n~~~bash\nnpm run lint\n~~~\n\nTarget: zero lint errors. Avoid aggressive style rules that create noise. Correctness and maintainability are more important than cosmetic formatting.\n\n## 8. LoadingManager audit\nTrace the complete loading lifecycle.\n\nVerify:\n- LoadingManager cannot initialize the scene twice;\n- critical promises always resolve or reject;\n- failed optional assets cannot deadlock loading;\n- failed critical assets produce a controlled failure;\n- loading progress cannot become NaN;\n- loading overlay cannot remain permanently stuck;\n- loader removal and scene initialization cannot race;\n- every async loader has a deliberate failure strategy.\n\nRecommended conceptual state machine:\n\n~~~text\nBOOT → LOADING → READY → PLAYING → PAUSED → DISPOSED\n~~~\n\nReject invalid transitions unless they are explicitly part of the existing design.\n\n## 9. Promise and async safety\nNever use empty failure suppression such as catch(() => {}) unless the operation is explicitly optional and the fallback is documented.\n\nFor critical operations use try/catch or an explicit rejection path. For optional operations use a named fallback handler.\n\nEvery async operation must answer:\n1. What happens if it succeeds?\n2. What happens if it fails?\n3. Can it finish after a newer request?\n4. Can it leave stale state behind?\n5. Can its rejection become unhandled?\n\n## 10. DOM safety\nAudit every querySelector/getElementById call.\n\nCheck:\n- required elements are validated;\n- optional elements have safe fallbacks;\n- event listeners are not registered twice;\n- stale DOM references are not reused after replacement;\n- duplicate IDs do not exist;\n- innerHTML is only used intentionally.\n\nDo not add meaningless null checks everywhere. Required elements should fail clearly during initialization if they are missing.\n\n## 11. Three.js resource integrity\nAudit Scene, Object3D, Mesh, Material, Texture, BufferGeometry, AnimationMixer, AnimationAction, and RenderTarget ownership.\n\nLook for:\n- use before initialization;\n- use after disposal;\n- duplicate resources;\n- accidental disposal of shared resources;\n- orphaned objects;\n- stale references;\n- repeated traversal/searches;\n- invalid transforms.\n\nEvery permanently removed resource must have a clear disposal owner.\n\n## 12. GLTF and OBJ tests\nFor every model test:\n- file exists;\n- model resolves;\n- expected scene hierarchy exists;\n- expected meshes exist;\n- animations exist where required;\n- materials resolve;\n- textures resolve;\n- transforms contain finite values.\n\nTest missing, corrupt, slow, and partially unavailable model assets. Optional assets must not crash the entire game.\n\n## 13. Character loading race conditions\nCharacter selection and preview loading are asynchronous.\n\nTest rapid sequences such as:\n\n~~~text\nWarrior → Wizard\nWarrior → Rogue → Ranger\nrapid repeated selection\nslow network + rapid selection\nfailed model + new selection\n~~~\n\nRequirement: an older asynchronous request must never overwrite a newer selection.\n\nUse request tokens/generation IDs or equivalent only where required. Do not rewrite the character system unnecessarily.\n\n## 14. AnimationStateMachine\nAudit AnimationStateMachine.js for:\n- invalid clip names;\n- missing actions;\n- repeated action creation;\n- invalid transitions;\n- duplicate play calls;\n- missing fallbacks;\n- mixer lifecycle problems.\n\nEvery requested gameplay animation must either resolve to a valid action or use a documented fallback.\n\nDo not solve missing animations by silently ignoring gameplay state.\n\n## 15. GameManager\nTest:\n- local player creation;\n- bot creation;\n- removal;\n- duplicate IDs;\n- scene registration;\n- restart;\n- respawn;\n- character changes;\n- cleanup.\n\nCheck for stale references after disconnect, restart, or character replacement.\n\n## 16. NetworkManager and Socket.IO\nTest:\n- normal connection;\n- server unavailable;\n- connection failure;\n- disconnect;\n- reconnect;\n- tab visibility changes;\n- malformed payload;\n- empty payload;\n- duplicate events.\n\nEnsure reconnects cannot create duplicate sockets or duplicate event listeners.\n\nValidate remote values before using them in Three.js or Cannon:\n\n~~~js\nNumber.isFinite(value)\n~~~\n\nReject NaN, Infinity, undefined, and invalid IDs/states safely.\n\n## 17. Physics / Cannon-es\nAudit PhysicsWorld.js and all world.step calls.\n\nVerify:\n- intended physics step frequency;\n- no duplicate physics steps;\n- bodies are created once;\n- bodies are removed correctly;\n- collision handlers use valid bodies;\n- no stale references remain;\n- no NaN positions/velocities/quaternions.\n\nDo not reduce solver quality or change physics behavior merely to make tests pass.\n\n## 18. NaN and Infinity investigation\nPay special attention to:\n- division;\n- normalize on zero-length vectors;\n- interpolation;\n- network values;\n- physics values;\n- delta time;\n- distances;\n- quaternion operations.\n\nA single NaN can propagate through an entire Three.js scene. Development-only finite-value assertions are encouraged for difficult systems.\n\n## 19. requestAnimationFrame audit\nSearch the entire repository for requestAnimationFrame.\n\nIdentify the single owner of the main render loop and verify:\n- initializeScene cannot create duplicate loops;\n- restart cannot create duplicate loops;\n- disposal stops the loop;\n- paused/ad states do not continue unnecessary work;\n- delta time is calculated consistently.\n\n## 20. Event listener lifecycle\nSearch every addEventListener, removeEventListener, socket.on, and socket.once.\n\nFor each listener document:\n- owner;\n- registration point;\n- cleanup point;\n- whether it can be registered twice;\n- stable callback reference.\n\nTest repeated start/restart/disconnect cycles. Watch for steadily increasing listeners.\n\n## 21. InputManager\nTest keyboard, mouse, pointer, double-click, context menu, and touch behavior.\n\nTest after:\n- browser blur;\n- alt-tab;\n- tab switching;\n- returning from an ad;\n- mobile browser suspension;\n- reconnect.\n\nTransient input must not become permanently stuck.\n\n## 22. Audio\nTest:\n- AudioContext suspended;\n- user gesture required;\n- audio buffer missing;\n- audio load failure;\n- repeated play;\n- repeated pause;\n- restart.\n\nAudio failure must never crash gameplay.\n\n## 23. WebGL and shader testing\nInspect grass, sky, rock, and every custom GLSL shader.\n\nCheck for:\n- shader compilation errors;\n- undeclared variables;\n- mismatched varyings;\n- wrong uniform types;\n- invalid precision assumptions;\n- invalid texture usage;\n- framebuffer errors.\n\nWhen a shader fails:\n1. Capture the exact browser/compiler error.\n2. Identify shader and line.\n3. Find root cause.\n4. Make the smallest fix.\n5. Rebuild.\n6. Retest visually.\n\nNever hide shader errors.\n\n## 24. Visual regression\nEvery debugging change must preserve:\n- six characters;\n- floating island;\n- grass appearance and density;\n- sky;\n- clouds;\n- day;\n- evening;\n- night;\n- day/night transition;\n- combat effects;\n- animation;\n- camera;\n- HUD.\n\nUse before/after screenshots or recordings when practical.\n\n## 25. Performance regression protection\nTesting must not undo the previous optimization work.\n\nRe-check:\n- grass rendering;\n- renderer pixel ratio;\n- asset loading;\n- duplicate resource requests;\n- startup time;\n- draw calls where measurable;\n- frame-time spikes.\n\nUse POKI_PERFORMANCE_OPTIMIZATION.md together with this document.\n\n## 26. Production logging policy\nDevelopment diagnostics may be verbose. Production should not be.\n\nTarget:\n- 0 per-frame logs;\n- 0 loading-progress spam;\n- 0 repeated animation logs;\n- 0 normal connection spam;\n- 0 debug GUI in production unless explicitly required.\n\nDo not simply delete console.error calls that represent real failures. Replace them with controlled error handling where appropriate.\n\nPrefer build-time development checks such as import.meta.env.DEV.\n\n## 27. Error handling policy\nClassify errors:\n\n### Critical\nRenderer failure, required shader failure, critical asset failure, or unrecoverable initialization failure.\n\nResult: controlled failure state; no infinite retry loop.\n\n### Non-critical\nOptional audio, preview asset, or decorative asset failure.\n\nResult: development diagnostic + safe fallback + gameplay continues.\n\nNever hide the root cause.\n\n## 28. Memory and disposal testing\nRun at least 10 repeated sessions:\n\n~~~text\nStart → Play → Restart → Play → Restart → ...\n~~~\n\nMonitor:\n- geometries;\n- textures;\n- materials;\n- scene objects;\n- animation mixers;\n- physics bodies;\n- sockets;\n- timers;\n- DOM listeners.\n\nMemory/resource counts should not grow continuously after repeated restarts.\n\n## 29. Browser matrix\nTest at minimum where available:\n- Chrome/Chromium;\n- Edge;\n- Firefox;\n- Android Chrome;\n- iOS Safari.\n\nCheck WebGL, shaders, audio, pointer input, touch, resizing, asset loading, and networking.\n\nDo not add browser-specific hacks without a reproducible browser-specific defect.\n\n## 30. Failure-injection tests\nIntentionally test:\n- missing texture;\n- missing GLTF;\n- missing OBJ;\n- corrupt asset;\n- slow asset;\n- failed network;\n- server unavailable;\n- malformed socket payload;\n- AudioContext unavailable;\n- browser tab suspension;\n- rapid character selection.\n\nEvery failure must produce controlled behavior.\n\n## 31. Build gate\nRun:\n\n~~~bash\nnpm run build\n~~~\n\nProduction build must have no syntax errors, import errors, missing shader imports, or broken asset references.\n\nIf lint exists:\n\n~~~bash\nnpm run lint\n~~~\n\nIf browser tests exist, run the configured test command and record the actual result.\n\n## 32. Smoke-test flow\nMinimum browser smoke test:\n\n~~~text\nOpen game\n→ loading overlay appears\n→ critical assets finish\n→ scene initializes once\n→ renderer produces frames\n→ player can interact\n→ character selection works\n→ day/night works\n→ restart works\n→ no unexpected console error\n→ no unhandled rejection\n~~~\n\n## 33. Multiplayer smoke test\nIf multiplayer is enabled:\n\n~~~text\nConnect → Join → Receive player state → Move → Disconnect → Cleanup → Reconnect\n~~~\n\nVerify no duplicate listeners, stale players, duplicate sockets, or uncaught errors.\n\n## 34. Code-quality rules\nPrefer:\n- clear names;\n- small single-purpose functions;\n- explicit state transitions;\n- cached references in hot paths;\n- meaningful constants;\n- accurate comments;\n- minimal nesting;\n- consistent error handling.\n\nAvoid:\n- speculative abstractions;\n- giant rewrites;\n- silent fallbacks;\n- magic behavior changes;\n- dead code left after a confirmed fix.\n\n## 35. Refactoring rules\nRefactor only when:\n1. The current behavior is understood.\n2. There is a real correctness or maintainability reason.\n3. The new implementation is simpler or safer.\n4. Regression testing covers the affected behavior.\n\nDo not turn one working module into many abstraction layers without evidence that it improves the project.\n\n## 36. Git discipline\nPrefer focused commits:\n\n~~~text\nfix: remove runtime errors\nfix: harden asset loading\nfix: stabilize character selection\nfix: harden network lifecycle\nrefactor: improve code readability\ntest: add browser smoke checks\nchore: remove production debug logging\n~~~\n\nAvoid mixing unrelated formatting, optimization, and gameplay changes.\n\n## 37. Required final report\nAt completion provide:\n\n~~~text\nERRORS FIXED\n[file] — [error] — [root cause] — [fix]\n\nWARNINGS ADDRESSED\n[warning] — [reason] — [result]\n\nCODE QUALITY\n[change] — [reason]\n\nBUILD\nnpm run build: PASS/FAIL\n\nLINT\nPASS/FAIL/NOT CONFIGURED\n\nRUNTIME\nUncaught exceptions: X\nUnhandled rejections: X\nUnexpected console errors: X\nUnexpected warnings: X\n\nWEBGL\nShader errors: X\nContext errors: X\n\nNETWORK\nNormal flow: PASS/FAIL\nFailure injection: PASS/FAIL/NOT TESTED\n\nREGRESSION\nGameplay: PASS/FAIL\nVisuals: PASS/FAIL\nMultiplayer: PASS/FAIL/NOT TESTED\nMobile: PASS/FAIL/NOT TESTED\n\nREMAINING ISSUES\n[honest list]\n~~~\n\nNever invent a PASS result.\n\n## 38. Definition of Done\n- Production build succeeds.\n- Syntax and module resolution are clean.\n- No uncaught runtime exceptions in normal tested flows.\n- No unhandled promise rejections.\n- No shader compilation errors.\n- Required assets load correctly.\n- Character loading is race-safe.\n- Physics does not produce invalid numeric state.\n- Network lifecycle is stable.\n- Input does not become stuck.\n- Audio failures are non-fatal.\n- Production debug tooling/log spam is removed or build-gated.\n- Event listeners and resources have controlled lifecycles.\n- Repeated restart testing does not reveal obvious leaks.\n- Existing gameplay is unchanged.\n- Existing visual design is unchanged.\n- Six characters remain.\n- Floating island remains unchanged.\n- Grass remains unchanged.\n- Sky and day/night transitions remain unchanged.\n- Performance work from POKI_PERFORMANCE_OPTIMIZATION.md remains intact.\n- Final report contains only real test results.\n\n## 39. Agent operating principle\nAct like a senior production Three.js/WebGL engineer and QA specialist.\n\nDo not guess.\nDo not hide errors.\nDo not rewrite working systems unnecessarily.\nDo not optimize away visible features.\nReproduce first, identify the root cause, make the smallest safe fix, build, run, and regression-test.\n\nFinal rule:\n\n~~~text\nREAD → REPRODUCE → DIAGNOSE → MINIMAL FIX → BUILD → TEST → REGRESSION → DOCUMENT\n~~~\n\nAn error is not fixed because the console is quiet. It is fixed when the underlying failure is understood and the affected gameplay path has been verified.
